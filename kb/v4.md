# The v4 rewrite (WIP)

> **Status: work in progress.** Everything on this page describes the `v4` git branch, which is under active development. It is **not** in production - the other pages in this KB document the production (`main`) architecture. Read this page if you want to follow or contribute to the rewrite.

The `v4` branch ([first commit](https://github.com/easydiffusion/easydiffusion/branch/v4): *"Initial commit of ED v4's rewrite of the internals. WIP"*) rebuilds the server-side of Easy Diffusion while keeping the existing frontend and the same four engine backends. The `sdkit3` *engine* itself (the C++ stable-diffusion.cpp backend) is already shipped and documented in [`backend-engines.md`](backend-engines.md#engine-comparison); what's WIP is the **server internals** around it. Direction-wise: the v4 engine is intended to become Easy Diffusion's **default engine going forward** (today's `ed_diffusers` default is a legacy-compatible choice, not a recommendation - see [`backend-engines.md`](backend-engines.md#engine-comparison)).

## Motivations

Distilled from the branch's commit history:

- **A cleaner REST API.** The ad-hoc routes (`/render`, `/filter`, `/get/*`, `/ping`) are replaced by a versioned `/v1` API. Old paths remain temporarily through a compatibility layer (below) so existing clients and plugins don't break on day one.
- **User-scoped tasks.** A simple users system was added; tasks are scoped by user, and each user gets their own config section.
- **A revamped config format.** `config.yaml` is managed by a dedicated `ConfigManager` (ruamel.yaml, comment-preserving, deep-merged partial updates) with a small set of system keys and per-user settings - replacing the stringly-typed dict that `app.getConfig()` returned.
- **Task-agnostic worker infrastructure.** The render-thread model in `task_manager.py` is generalised into `workers.py` (`Task`, `Worker`, `Workers`) that doesn't care what kind of task it runs (image generation today, other task types later), with progress tracking built into the task object.
- **Typed request/response models.** `models.py` moves the loose dicts to pydantic models with response-model validation on every route.
- **Testability.** A pytest suite (below) covers workers, config, and server endpoints - something the production tree never had.

## The new layout (v4 branch)

| Production (`main`) | v4 branch |
| --- | --- |
| `ui/easydiffusion/server.py` (legacy routes) | `easydiffusion/server.py` - FastAPI app with a versioned router (`APIRouter(prefix="/v1")`) |
| - | `easydiffusion/legacy_server.py` - `support_legacy_paths()` registers the old endpoints (`POST /render`, `POST /filter`, `GET /get/models`, `/get/system_info`, `/get/modifiers`, `/get/ui_plugins`) and translates legacy request formats, so older clients keep working |
| `ui/easydiffusion/task_manager.py` | `easydiffusion/workers.py` - `Task` (status, progress, outputs), `Worker` (one per device), `Workers` (pool management, backend switching) |
| `ui/easydiffusion/app.py::getConfig/setConfig` | `easydiffusion/config.py` - `ConfigManager`, `create_default_config`, `SYSTEM_CONFIG_KEYS = ("network", "updates", "models", "backend")`, per-user config with deep merge |
| `ui/easydiffusion/types.py` (dataclasses) | `easydiffusion/models.py` (pydantic models) |
| module-level backend functions | `easydiffusion/backends/` - class-based: `base.py` defines a `Backend` ABC (device-aware: receives a torchruntime `GPU` object), and `BACKEND_REGISTRY` maps names to `EDClassicBackend`, `WebUIBackend`, `Sdkit3Backend`, `TestBackend` |
| - | `easydiffusion/main.py` - new entry point (creates the default config, requires at least one configured user, wires config → workers → server) |
| - | `tests/` - pytest suite (below) |

The frontend (`ui/`) stays; it was adapted to the new API data format *"while still retaining the old JS-side data structs for plugin compatibility"* (commit 2b461ecb).

## The /v1 API

Registered on the versioned router (`easydiffusion/server.py`):

- **Status:** `GET /v1/status` (replaces `/ping`)
- **Config:** `GET /v1/config`, `PUT /v1/config`; per-user: `GET|PUT /v1/users/{username}/config`
- **Devices:** `GET /v1/devices`
- **Models:** `GET /v1/models`
- **Tasks:** `POST /v1/tasks` (create; accepts both generate and filter requests), `GET /v1/tasks` (list, filterable by user), `GET /v1/tasks/{task_id}` (detailed), `GET /v1/tasks/{task_id}/outputs/{output_id}` (fetch output bytes), `DELETE /v1/tasks/{task_id}` (stop), `DELETE /v1/tasks` (stop all)
- **Users:** `GET /v1/users`, `POST /v1/users`, `DELETE /v1/users/{username}`

`GET /v1/devices` lists the available devices; internally, v4 passes torchruntime `GPU` objects to backends so they can pick runtime variants with richer information (commit 054b05c8) - a deliberate improvement over the string device ids on `main`.

## Testing

The rewrite ships with a pytest suite (see [`testing.md`](testing.md)):

- `tests/integration/test_worker_management.py` - worker lifecycle end-to-end: workers starting at app startup, live reconfiguration via `PUT /v1/config`, device selection and overload behaviour, using a registered dummy backend from `tests/support.py`.
- Unit tests: `tests/test_config.py`, `tests/test_server.py`, `tests/test_workers.py`, `tests/test_models.py`, `tests/test_device_utils.py`, with fixtures in `tests/conftest.py`.

Run from a `v4` checkout: `pytest tests/`.

## Trying it

1. Clone the repo and check out `v4`.
2. Follow the [`development.md`](development.md) install-and-symlink workflow (the `ui/` folder is shared between branches).
3. sdkit v3 (the v4 engine's stack) lives on the sdkit repo's `v3` branch for now - see the note in [`backend-engines.md`](backend-engines.md#engine-comparison).

User-facing details of the v4 engine (install footprint, Vulkan backend for AMD/Intel/older GPUs, stable-diffusion.cpp/ggml underpinnings) are on the wiki's [`v4`](https://github.com/easydiffusion/easydiffusion/wiki/v4) page.
